## Verdict

I chose **Strategy B** (structured context: AGENTS.md + file summaries) for the final architecture doc. It was the only draft that captured the repo as a whole — CI, the unused DELETE endpoint, the sort rule, partial-update semantics — and every contested claim I spot-checked against the code held up. Its two gaps are omissions, not errors: `backend/Dockerfile` and README's stale `tests/verify_a.py` path, so I patch those from A (the stale-path flag) and C (the `get_all_tasks()` docstring gap) rather than re-drafting. A was faster but confidently wrong twice (CORS origins, `updated_at` on empty PATCH), and C traded away coverage it needed — epistemic hygiene without the architecture.

## Context-engineering rule

For a full-repo architecture document, I use structured context (AGENTS.md + file summaries) because it gave the widest accurate coverage at a bounded reading cost and every spot-checked claim held up. For read-only inspection where overclaiming is forbidden, I use targeted anchor files (Strategy C) because explicit read/not-read markers are the only way to keep every claim traceable to an inspected file.
