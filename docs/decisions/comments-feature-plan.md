### Generic vs repo-grounded comparison

- **Biggest difference:** the generic plan is an assumption list that defers every repo-specific decision to "whatever the repo does" ("pick one and document it", "repo convention wins"); the repo-grounded plan replaces each deferral with a verified precedent and a file:line anchor (ActivityEvent as the sibling model, `delete_task`/`_reset` as the two mandatory integration points, the edit modal's `#activity-section` as the UI home) — and every substantive anchor I spot-checked held.
- **Plan I'd hand to a teammate:** the repo-grounded one — ~30 line-number claims verified true, it pre-flags repo drift a teammate would otherwise trip on (verify_a.py actually lives in [backend/scripts/](backend/scripts/), backend/README.md's stale "no ci.yml" note), and its only flaws are two one-line test fixes (cascade assertion, isolation test); the generic plan would cost a teammate a day of rediscovering those same conventions.
- **Task shape where generic chat is enough:** greenfield design-space work — no codebase to ground against, where the deliverable is enumerating the options (immutability, ordering, pagination, auth, nesting style) for a human to decide; there the generic plan's open-questions list is essentially as good as the grounded one's.
